## Primary repair being validated

The v1.2 repair is focused on the auto-inactive/reactivation lifecycle.

Expected rule:

* A cycle member who misses a valid submission receives the configured no-submission penalty.
* The first 4 consecutive missed scoring days each receive the no-submission penalty.
* After the 4th consecutive missed scoring day closes, the participant becomes inactive for scoring purposes.
* While inactive, missed scoring days are worth 0 points.
* A valid participant submission during an allowed submission window reactivates the participant for that score day.
* The reactivation submission counts normally.
* Reactivation resets the missed-day streak.
* If the participant later misses 4 consecutive scoring days again, the inactive behavior repeats.
* Archived participants must not be reactivated by this logic.
* Non-cycle members must not be included in this logic.

## Critical pass/fail rules

This v1.2 test passes only if:

* Valid submissions are accepted.
* Duplicate submissions are rejected.
* Invalid-window submissions are rejected.
* Invalid scores are rejected or prevented.
* Rejected actions do not create records.
* Corrections still affect totals correctly.
* Corrections do not allow non-cycle members for the selected score day.
* Archived participants remain excluded from normal workflows.
* Active-cycle reports only use elapsed days.
* Display-name-only exports remain correct.
* P5 receives missed-day penalties for only the first 4 consecutive missed scoring days.
* P5 receives 0 points for missed days after becoming inactive.
* P5 reactivates after a valid submission.
* P5's reactivation submission counts normally.
* P5's missed-day streak resets after reactivation.
* Reports, leaderboard, admin views, and membership views agree.

This v1.2 test is a hold/fail if:

* P5 continues accumulating -3 after the inactive threshold.
* P5 does not reactivate after a valid submission.
* P5's valid reactivation submission does not count.
* Reports and admin/member state disagree in a way that cannot be explained.
* Rejected actions create data anyway.
* Archived/non-cycle participants appear in normal participant workflows.
* Any repaired alpha/beta critical issue reappears.
